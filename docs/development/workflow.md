# 2인 협업

Linear Project/Milestone/Issue로 요구·진행을 관리하고 GitHub로 코드·계약·ADR·검증 근거를 관리한다. 문서 전체를 양쪽에 복제하지 않고 연결한다.

## Ready → PR → Done

1. 사용자 기능 중심 상위 Issue에서 목표·제외 범위·수용 기준을 정한다. 독립 검증/차단 의존성이 있는 경우만 기술 하위 Issue를 만든다.
2. Ready: 입력/출력과 수용 기준이 명확하고 SDK 미확인 사항·검증 방식·의존성·승인 필요 행동이 기록돼 착수 가능하다. 실제 워크스페이스에 Ready라는 상태가 없으면 같은 기준을 label/본문으로 표현한다.
3. 두 사람 누구나 Ready Issue를 선택한다. 착수자/진행 상태를 공유하고 짧은 feature branch를 만든다. Android/MCP 고정 담당자는 두지 않는다.
4. 최소 변경과 적절한 검증 후 PR에 Linear 링크, 문제/결과, 실제 검증·미실행 이유, 계약/ADR 영향을 적는다.
5. 상대 개발자가 리뷰한다. Agent 검토가 사람의 상호 리뷰를 대체하지 않는다. 공통 계약/ADR 변경은 합의 후 병합한다. 새 코드는 통합 가능한 작은 단위로 main에 자주 합친다.
6. Done: 수용 기준 증거, 해당 CI 통과, 상대 승인, main 병합, 코드/계약/아키텍처 문서 일치 및 Linear 결과 링크가 갖춰진 상태다. 빌드만 통과한 기능은 Done이 아니다.

## Agent 작업

작업 시작 시 remote/branch/status와 Issue 범위를 확인한다. main 직접 수정, 사용자의 미커밋 변경 덮어쓰기, 무관한 정리/업그레이드를 피한다. 모호한 구현은 작은 안전한 가정으로 진행하되 SDK 지원·실행 결과를 만들어내지 않는다.
외부 공개, 차량 명령, 연락 전송은 별도 사용자 권한을 확인한다. PR에는 로그/스크린샷의 비밀·개인정보가 없는지 확인한다.

Branch protection/required checks 설정은 저장소 운영자가 확인한다. 이 문서는 보호 규칙이 서버에서 강제되고 있다는 증거가 아니다.
