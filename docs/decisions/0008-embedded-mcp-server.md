# ADR-0008: MCP 서버를 차량 앱 안으로 옮긴다

- 날짜: 2026-11-08
- 상태: 제안 (COM-12 PR에서 상대 개발자 합의 필요)
- 대체: [ADR-0002](0002-boundaries-and-transport.md), [ADR-0005](0005-mcp-typescript-and-tooling.md), [ADR-0003](0003-single-repository.md)의 `mcp/` 부분
- 근거: [ADR-0007](0007-embedded-mcp-go-no-go.md)의 Go 제안(PR #12), COM-12

## 맥락

[ADR-0001](0001-external-mcp-first.md)은 1차를 외부 Node MCP로 하고, 앱 내장은 따로 검증하기로 했다. COM-13 실험(ADR-0007) 뒤 두 개발자는 COM-12·15에서 MCP 서버를 앱 안으로 옮기고 Node·TypeScript를 없애기로 했다.

COM-12에서 확인한 것(PR #15):
- **계약 동등성:** 같은 fixture로 Node와 앱 서버를 검사했다. `tools/list`, 인자 판정, 결과 23건의 글과 structuredContent가 같았다.
- **에뮬레이터 비교:** debug·release에서 각각 두 경로를 100회 호출해 결과가 같았다.
- **실제 AI 호출:** Codex로 실행했다.
  - 1차(추론 강도 low): 요구사항 6.2 기준 0/8. 모두 5초를 넘었고, 도구 미호출이 1회 있었다.
  - 2차(medium): 사용자가 정한 "정답 여부" 기준으로 8/8.
  - Claude 계열은 확인하지 않았다.

## 결정

**전송**
- 차량 앱이 Foreground Service 안에서 MCP 서버를 연다.
  - 주소: `127.0.0.1:18766/mcp`
  - 전송: stateless Streamable HTTP
  - 구현: MCP Kotlin SDK 0.16.0, Ktor 3.5.2 CIO
- 도구는 카탈로그에서 `adopted`인 것만 내놓는다. 이름, 입력, 결과 글, 오류 의미는 [차량 조회 계약](../../contracts/vehicle-read/CONTRACT.md)을 따른다.
- PC의 Node 서버와 `127.0.0.1:18765` HTTP Bridge는 없앤다.
  - 게이트웨이와 그 응답 형식은 앱 안 경계로 남는다.
  - MCP 서버는 게이트웨이 응답을 계약 검증한 뒤에만 결과로 쓴다.

**책임**
- 외부 AI: 사용자 맥락과 도구 선택
- 앱 MCP 서버: MCP 입출력, 인자 검사, 결과 형식
- Android Adapter: SDK 접근
- Service: 세션 자원(서버, 게이트웨이, 읽기 슬롯)을 소유한다.

**인증·권한**
- 1차는 인증을 두지 않는다(COM-12 결정).
- Host 허용 목록과 Origin 거부는 브라우저식 요청만 막는다. 호출자를 확인하지 않는다.
- 차량 권한(`CAR_*`)은 앱이 가지며, 서버가 열려 있는 동안 기기의 다른 앱도 이 권한을 거쳐 읽기 값을 얻을 수 있다.
- 노출 범위는 카탈로그의 읽기 값이다. 제어 API는 없다.

**생명주기**
- 서버는 사용자가 연결을 시작해야 열리고, 중지하면 닫힌다. 중지 순서는 승인 차단 → 서버 종료 → 대기 요청 취소다.
- 앱 전체에 읽기 슬롯이 하나다. 큐는 없고, 동시 호출은 `BUSY`를 받는다.
- 데드라인은 10초이고, 어느 계층도 자동 재시도하지 않는다.

**외부 접근**
- 개발 PC의 AI 클라이언트가 `adb forward tcp:18766`으로 연결한다. 요구사항 NFR-02(개발 PC 범위)와 같다.
- 외부 네트워크에 공개하지 않는다.
- PC·ADB 없이 연결하는 경로(COM-15)는 이 ADR에서 정하지 않는다.
  - COM-15는 "공개 인바운드 포트 없이"를 요구한다.
  - ChatGPT·Claude의 원격 커넥터는 자기 클라우드에서 공개 HTTPS로 접속한다.
  - 그래서 그 경로에는 서버 운영, 인증, 공개 범위 결정이 함께 필요하다. NFR-02와도 충돌하므로 별도 ADR로 정한다.

**롤백**
- 이 전환은 두 PR로 나뉜다. 내장 서버 추가(PR #15)와 Node·Bridge 제거(이 ADR의 PR)다.
- 제거 PR을 revert하면 Node 서버, 18765 Bridge, 그 테스트와 CI job이 돌아온다. 그 상태에서는 두 경로가 함께 동작한다.
- revert 후 Node 경로로 `get_energy_level`을 Console 값과 대조한 기록을 제거 PR에 남긴다.

## 대안

- **Node 경로 유지:** 기술 스택이 Kotlin + Android와 Node + TypeScript 둘로 남는다. 계약을 두 언어로 지켜야 한다.
- **stateful Streamable HTTP:** ADR-0007에서 버렸다. 세션 삭제 없이 떠난 클라이언트가 쌓여 새 접속이 거부됐다.
- **인증 추가(설치별 토큰 등):** 다른 앱의 접근을 막는다. 대신 토큰을 클라이언트로 옮기는 절차가 생기고, 토큰이 기록·영상에 남지 않게 관리해야 한다(NFR-03). 1차에서는 넣지 않고, COM-15의 외부 접근과 함께 다시 정한다.

## 결과

**좋아지는 점**
- PC의 Node 프로세스가 없어진다.
- 계약을 Kotlin 한 곳에서 지킨다.
- 도구 호출 시간은 에뮬레이터 중앙값 기준 107ms에서 약 30ms로 줄었다. 차이의 대부분은 옛 Bridge의 100ms 대기 주기에서 왔으므로 내장 방식의 이점으로 보지 않는다.

**비용**
- 런타임 의존성이 79개에서 131개로 늘었다.
- release APK가 2.94MB에서 3.97MB로 커졌다.
- R8 규칙 2줄이 필요하다(Ktor의 `java.lang.management` 참조).
- Kotlin 2.4와 AGP 9.5가 필요하다(PR #13).

**잃는 것**
- Ktor CIO는 클라이언트가 떠나도 호출을 취소하지 않는다.
  - 떠난 클라이언트의 조회도 끝까지 슬롯을 쓴다.
  - 화면의 "조회 중 연결 끊김" 상태가 더 이상 나오지 않는다.
- 서버가 스스로 멈춰도 감지하지 못한다.
- 전수 실행 도구(`:vehicle-sweep`)는 MCP로 부르므로 채택된 도구만 판정한다.
- COM-10 모의 진입점이 없어졌다.

**남은 위험**
- 인증이 없다.
- Claude 계열 연결을 확인하지 않았다.
- 6.2의 5초 목표를 Codex로 맞추지 못했다(앱 안 조회는 수십 ms).
- 앱마켓 보안 가이드의 HTTPS·노출 최소화 원칙에 loopback HTTP가 해당하는지 확인하지 않았다.
